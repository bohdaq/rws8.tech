Config-Driven Proxy

When rws.config.toml (or the file pointed to by RWS_CONFIG_FILE) contains at least one [[route]] or [[upstream]] section, rws boots in proxy mode automatically. No code changes required.

Minimal example

Section titled “Minimal example”

[[upstream]] — backend pools

Section titled “[[upstream]] — backend pools”

Each [[upstream]] block defines a named pool of HTTP or HTTPS backends.

  • round_robin (default) — cycles through live backends in order.
  • random — picks a live backend at random on each request.
  • ip_hash — hashes the client IP so the same client always reaches the same backend (useful for WebSocket/SSE stickiness without shared session state).
  • least_connections — routes to whichever live backend currently has the fewest in-flight requests through this route.

An unrecognized or empty strategy value falls back to round_robin.

Performance

Section titled “Performance”

A proxy route with no [route.middleware] and no global [middleware] is forwarded without blocking a thread — HTTP and HTTPS upstreams alike, including tls_ca_file ones: the request waits for the backend on its connection’s own task, over pooled keep-alive connections. Routes with middleware use a thread from the blocking pool for the round trip — still pooled, slower under heavy concurrency. See Benchmarks.

TLS (HTTPS) upstreams

Section titled “TLS (HTTPS) upstreams”

Prefix backend addresses with https:// to connect over TLS. Certificate verification uses the WebPKI root store (same CA bundle as browsers). TLS connections are kept alive and reused, like plain ones — one handshake per connection, not per request — and large or chunked responses are streamed.

For internal services behind a private CA or a self-signed certificate, name the CA to trust with tls_ca_file. It replaces the public roots for that upstream — requests and health checks alike — so only certificates issued by that CA are accepted:

A CA file that can’t be read fails closed: the upstream answers 502 and the error is logged, rather than falling back to the public roots. rws --check reports it. A reload re-reads the file, so a rotated CA takes effect on SIGHUP.

Feature requirement

HTTPS upstreams require the http-client or http2 feature — both are included in the default (http3) build and the http2-only build. The http1-only build (--no-default-features --features http1) returns 502 for HTTPS backends and logs an error.

[upstream.health_check] — automatic health monitoring

Section titled “[upstream.health_check] — automatic health monitoring”

Add a nested [upstream.health_check] table to enable background health checking. Unhealthy backends are removed from the live rotation until they recover.

See Health Checks for the full implementation details.

Weights, stickiness, retries and the circuit breaker

Section titled “Weights, stickiness, retries and the circuit breaker”

Since 18.6.0 an [[upstream]] takes the same traffic policies as the library proxy:

  • weights — round_robin spreads requests in proportion to the weights without sending runs to one backend (smooth weighted round-robin, as nginx does: 3:1:1 goes a b a c a); random picks in proportion to them; least_connections compares in-flight requests per unit of weight. ip_hash ignores them.
  • [upstream.sticky] — the first response to a client sets Set-Cookie: <cookie>=<id>; Path=/; HttpOnly; SameSite=Lax. The id is a hash of the backend URL, so it doesn’t reveal backend addresses and stays the same across restarts and replicas. A client that sends it goes to that backend while it is in rotation; otherwise (backend removed, ejected or failed on this request) the strategy picks another and the cookie is replaced.
  • [upstream.circuit_breaker] — passive health checking: every proxied request counts. No response, or a 502/503/504, is a failure; failure_threshold failures in a row take the backend out of rotation for recovery_secs, then half_open_probes requests are let through, and a success puts it back. It works with or without [upstream.health_check] (a backend has to pass both). When every backend is out, the route answers 503 Service Unavailable with Retry-After without contacting any.
  • [upstream.retry] — a request that got no response or one of the status codes is sent to up to attempts other backends. Only idempotent methods (GET, HEAD, OPTIONS, PUT, DELETE, TRACE) with a buffered body are retried; a POST or a streamed upload gets the first answer. The last answer is returned when every attempt fails.

rws --check validates them: weight counts that don’t match backends, a weight of 0, an invalid cookie name, failure_threshold = 0 and retry statuses outside 400–599 are errors; weights with ip_hash and attempts at or above the number of backends are warnings. Each upstream’s traffic shows up on /metrics.

[[route]] — routing rules

Section titled “[[route]] — routing rules”

Routes are evaluated in declaration order; the first match wins.

[route.match] — matching criteria

Section titled “[route.match] — matching criteria”

All fields are optional. Omitting a field means “match anything”.

Path matching rules:

Pattern Matches
/api/* Any path starting with /api/ (prefix match)
/api/ping Only /api/ping (exact match)
(omitted) All paths

Paths are normalized before any route is matched, and sent upstream in that form (since 17.113.1): percent-encoded unreserved characters are decoded (/%61dmin → /admin; %2F and other escapes stay encoded), repeated slashes collapse (//admin → /admin) and . / .. segments are resolved (/x/../admin → /admin). So a route that protects /admin/* can’t be skipped by spelling the path differently. host matches ignoring case, and ignoring the port unless the route names one.

[route.action] — what to do on match

Section titled “[route.action] — what to do on match”

The type field selects the action. An action’s keys may also sit directly under [route.action] instead of in [route.action.<type>] (type = "proxy" plus upstream = "api" in the same table); if a key appears in both, the nested table wins.

type = "proxy" — forward to an upstream

Section titled “type = "proxy" — forward to an upstream”

type = "grpc" — forward gRPC to an HTTP/2 upstream

Section titled “type = "grpc" — forward gRPC to an HTTP/2 upstream”

Requests go over HTTP/2 (since 18.3.0; before, this action used HTTP/1.1 and gRPC couldn’t work): every call type streams and the grpc-status trailers reach the client — see gRPC proxy. gRPC-web requests from browsers are translated to gRPC on the way (gRPC-web). Upstream backends are grpc://host:port / h2://host:port (cleartext) or grpcs://host:port / h2s://host:port (TLS, with the upstream’s tls_ca_file and tls_client_cert_file / tls_client_key_file).

type = "redirect" — HTTP redirect

Section titled “type = "redirect" — HTTP redirect”

type = "respond" — fixed response

Section titled “type = "respond" — fixed response”

type = "static" — serve a directory

Section titled “type = "static" — serve a directory”

Requests are resolved against root, independent of the server process’s working directory. Any request path containing a .. segment (before or after percent-decoding) is rejected with 403; a request that resolves to a missing file returns 404. Directory requests (or any path resolving to a directory) try each index entry in order and 404 if none exist. MIME type is detected from the file extension, matching the built-in static-file controller.

[route.middleware] — per-route middleware

Section titled “[route.middleware] — per-route middleware”

Middleware is applied only to requests that match this route.

Rate limiting

Section titled “Rate limiting”

Any sub-table can also be written inline under [route.middleware] — rate_limit = { max_requests = 100, window_secs = 60 } is the same as the [route.middleware.rate_limit] table above.

Authentication

Section titled “Authentication”

Three types, all under [route.middleware.auth]:

Bearer token — always available, no extra feature:

Incoming requests must include Authorization: Bearer <value of API_TOKEN>. Returns 401 Unauthorized on mismatch.

JWT (HS256) — requires the auth feature; wires into JwtLayer:

HTTP Basic (htpasswd file) — requires the auth feature; wires into BasicAuthLayer::from_htpasswd_file:

The htpasswd file supports plain-text and {SHA256} (rws’s own scheme) entries only — not Apache’s real {SHA}/$apr1$/bcrypt. See the auth feature page for the exact file format and how to generate a {SHA256} entry with openssl.

Fails closed, not silently

Auth fails closed. If token_env/secret_env/htpasswd_file is unset, empty, or unreadable — or the binary was built without the auth feature — that route answers 503 Service Unavailable (logged to stderr at startup) instead of being served unprotected. Other routes keep working. Check your server’s startup logs after changing [route.middleware.auth].

Request rewriting

Section titled “Request rewriting”

Request rule types: header_set (name, value), header_remove (name), uri_set (value), uri_strip_prefix / strip_prefix and uri_add_prefix / add_prefix (prefix, or value).

Response rewriting

Section titled “Response rewriting”

Response rule types: header_set (name, value), header_remove (name), status (code, reason), body_replace (from, to). An unknown type is ignored (and reported by rws --check).

Response caching

Section titled “Response caching”

Wraps the route in an in-memory CacheLayer (up to 1000 entries). It is the innermost route middleware, so cached responses still pass through rewrite, auth, rate limit and IP filter.

Per-route timeout

Section titled “Per-route timeout”

0/absent means no route-specific timeout. Bounds this route’s total time — every other middleware layer runs inside it. See Timeouts for the underlying mechanism and its one honest limitation (a synchronous handler that ignores its deadline keeps running in the background; only the client’s wait is bounded).

Per-route max body size

Section titled “Per-route max body size”

0/absent means no route-specific limit. This is a stricter, additional cap on top of the global RWS_CONFIG_MAX_BODY_SIZE_IN_BYTES (see Forms & Uploads) — not a substitute for it. It’s checked after this route has already been matched, which means the body was necessarily already read in full to build the Request that route matching itself required; use it to keep one route (e.g. a small JSON API) stricter than the global ceiling a separate upload route needs, not as protection against unbounded memory use — the global limit is what already provides that, for every route.

Global middleware

Section titled “Global middleware”

Middleware that applies to every request goes in a top-level [middleware] section (same field structure as [route.middleware]). It wraps the whole router: matched routes and requests that fall through to the static files, health checks and metrics. Per-route middleware runs inside it.
