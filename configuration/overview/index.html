Configuration Overview

rust-web-server uses a four-layer configuration system. Each layer can override the one below it. All resolved values are stored as process environment variables under the RWS_CONFIG_* namespace and read at request time — there is no config struct passed through the call stack.

Priority order (lowest to highest)

Section titled “Priority order (lowest to highest)”
Priority Source Notes
1 Built-in defaults Hardcoded in src/entry_point/mod.rs
2 System environment variables Set before the process starts
3 rws.config.toml Optional file in the working directory
4 CLI arguments Flags passed on the command line

A value set at a higher priority layer always wins. For example, --port=9000 on the command line overrides port = 8080 in rws.config.toml, which in turn overrides RWS_CONFIG_PORT=8888 in the environment.

What reloads

Section titled “What reloads”
Setting Environment variable
CORS — all fields RWS_CONFIG_CORS_*
Rate-limit thresholds RWS_CONFIG_RATE_LIMIT_MAX_REQUESTS, RWS_CONFIG_RATE_LIMIT_WINDOW_SECS
Log format RWS_CONFIG_LOG_FORMAT
Request allocation size RWS_CONFIG_REQUEST_ALLOCATION_SIZE_IN_BYTES
Security headers, CSP, client hints, nanosecond timestamps, static Cache-Control RWS_CONFIG_SECURITY_HEADERS, RWS_CONFIG_CSP, RWS_CONFIG_CLIENT_HINTS, RWS_CONFIG_NANOS_HEADERS, RWS_CONFIG_STATIC_CACHE_CONTROL
Proxy routes and upstreams [[route]], [[upstream]], [middleware] (kept as before if the new file has errors)
Tera templates re-globbed from RWS_CONFIG_TEMPLATE_DIR (tera feature)

On TLS builds, SIGHUP also rebuilds the TlsAcceptor from the updated certificate files for all virtual hosts — no restart needed to rotate certs.

What requires a restart

Section titled “What requires a restart”
Setting Reason
IP / Port The bound socket cannot be moved
Thread count The thread pool is fixed at startup
Enabling the global rate limit Decided once at startup (changing its numbers reloads)
[[tcp_proxy]], [[udp_proxy]], [[ws_proxy]] Listeners start once
TLS cert / key paths (plain HTTP build) The acceptor is built once

Rate-limit changes are instant

When a reload fires, the live global RateLimiter is updated in place via set_limits(). Existing per-IP counters are preserved — only the limit values change. The new limits apply to the very next request.

Reading config in handler code

Section titled “Reading config in handler code”

config_reload::current() returns a typed ConfigSnapshot containing all hot-reloadable values. It takes a brief read lock and clones a handful of strings — safe to call on every request.

The ConfigSnapshot fields map directly to environment variables:

Field Environment variable
cors_allow_all RWS_CONFIG_CORS_ALLOW_ALL
cors_allow_origins RWS_CONFIG_CORS_ALLOW_ORIGINS
cors_allow_credentials RWS_CONFIG_CORS_ALLOW_CREDENTIALS
cors_allow_methods RWS_CONFIG_CORS_ALLOW_METHODS
cors_allow_headers RWS_CONFIG_CORS_ALLOW_HEADERS
cors_expose_headers RWS_CONFIG_CORS_EXPOSE_HEADERS
cors_max_age RWS_CONFIG_CORS_MAX_AGE
rate_limit_max_requests RWS_CONFIG_RATE_LIMIT_MAX_REQUESTS
rate_limit_window_secs RWS_CONFIG_RATE_LIMIT_WINDOW_SECS
log_format RWS_CONFIG_LOG_FORMAT
request_allocation_size RWS_CONFIG_REQUEST_ALLOCATION_SIZE_IN_BYTES

Memory

Section titled “Memory”

rws reads each request in chunks of request_allocation_size_in_bytes (default 10000 bytes); larger bodies span several reads, and max_body_size_in_bytes caps them (0 = unlimited). Static files over 256 KiB are streamed from disk rather than buffered, and so are proxied upstream bodies over 1 MB.
