Config File (rws.config.toml)

rws.config.toml is an optional TOML file placed in the server’s working directory. It provides a convenient alternative to environment variables and CLI flags. Any key set here overrides the built-in default and any system environment variable, but can be overridden by a CLI flag.

The file is auto-detected at startup. Override the path with the RWS_CONFIG_FILE environment variable (used for both server settings and proxy routes):

Check the file before you deploy

Section titled “Check the file before you deploy”

rws --check validates the configuration without starting the server and exits 0 if it has no errors, 1 otherwise — like nginx -t:

With --format=json the report is one JSON object — {"path":…,"ok":…,"errors":[…],"warnings":[…]} — with the same exit codes.

It reports unknown keys anywhere in the file, values of the wrong type, certificate and key files that are missing or don’t load, ACME mistakes, proxy routes that point at undeclared upstreams, unknown action types, IP filter entries that aren’t addresses, and auth secrets that aren’t set. Secrets and files are checked in the current environment, so run it where the server runs. Proxy problems are also printed when the server starts.

The same checks are a library call, e.g. in a test that keeps a deployment’s config honest:

report.render_json(path) gives the --format=json output.

How keys map to settings

Section titled “How keys map to settings”

Every setting has an RWS_CONFIG_* environment variable. In the file, a key’s variable is its table name plus the key, upper-cased:

In rws.config.toml Setting
port = 443 (top level) RWS_CONFIG_PORT
[cors] allow_all = false RWS_CONFIG_CORS_ALLOW_ALL
[rate_limit] max_requests = 500 RWS_CONFIG_RATE_LIMIT_MAX_REQUESTS
2nd [[virtual_host]] block, domain = ... RWS_CONFIG_VIRTUAL_HOST_1_DOMAIN

Strings keep their exact contents (csp = "default-src 'self'; img-src *" works); arrays become comma-separated lists. A key that doesn’t correspond to any setting is reported at startup — Warning: unknown setting '[server] port' in rws.config.toml — ignored — rather than silently dropped. [[route]], [[upstream]], [[tcp_proxy]], [[udp_proxy]], [[ws_proxy]], and [middleware] tables configure the proxy (below) and aren’t settings.

An inline table is the same as a sub-table, here and in the proxy sections:

Proxy mode

When the file contains at least one [[route]] or [[upstream]] section, the server starts in proxy mode (ConfigDrivenApp). The built-in static-file and controller stack is used only as a fallback for unmatched requests.

Server settings (top level)

Section titled “Server settings (top level)”

Basic server settings go at the top of the file, before any [section] header. Each key maps to the RWS_CONFIG_* environment variable and the --flag of the same name (rws --help lists them all).

Caution

Don’t wrap these in a [server] table: keys are prefixed with their table’s name, so [server] port = 443 becomes --server-port, which doesn’t exist and is ignored.

[acme]

Section titled “[acme]”

Automatic HTTPS from Let’s Encrypt or another ACME CA (acme feature, included in the prebuilt binaries). Setting domains enables it. See Automatic HTTPS for how it works.

[cors]

Section titled “[cors]”

CORS policy applied to every response. All fields are hot-reloadable.

[rate_limit]

Section titled “[rate_limit]”

Global rate limit per client IP: requests over the budget get 429 Too Many Requests. Off unless max_requests is set — enabling it needs a restart; changing the numbers afterwards is hot-reloadable. For per-route limits in proxy mode use [route.middleware] rate_limit instead.

Request limits

Section titled “Request limits”

Fixed limits that apply whatever the configuration:

Limit Value Over the limit
Request head (request line + headers), HTTP/1.1 64 KiB 431 Request Header Fields Too Large
Header list, HTTP/2 and HTTP/3 64 KiB stream reset
Concurrent streams per HTTP/2 connection 250 stream refused
Idle time between reads 30 s connection closed
HTTP/2 connection with nothing running and nothing received 30 s GOAWAY(NO_ERROR), connection closed
HTTP/2 stream resets, the client’s or provoked by it (rapid reset, MadeYouReset) 1000 per 10 s GOAWAY(ENHANCE_YOUR_CALM)
Whole request head, from its first byte (HTTP/1.1) 30 s 408 Request Timeout
TLS handshake 10 s connection closed

The request body limit is max_body_size_in_bytes above. On HTTP/1.1, bodies may be sent with Content-Length or Transfer-Encoding: chunked; a request that carries both, or two different Content-Length values, is rejected with 400 so rws and a proxy in front of it can never disagree about where a request ends.

For the same reason an HTTP/1.1 request head is read strictly (17.113.2) and answered 400 when it has no Host or more than one, a method not in upper case (get), a version other than HTTP/1.0/HTTP/1.1, a folded header line (starting with a space or tab), whitespace before a header’s colon, or a header name with characters a token can’t have. Connection is read token by token: Connection: close, TE closes the connection after the response.

[[virtual_host]]

Section titled “[[virtual_host]]”

Repeat this section for each domain that needs its own TLS certificate. The SNI resolver selects the right certificate automatically at handshake time.

[[upstream]]

Section titled “[[upstream]]”

Defines a named backend pool. Upstreams are referenced by name from routes.

When the health checker removes all backends, the route returns 502 Bad Gateway until at least one backend recovers.

[[route]]

Section titled “[[route]]”

Each [[route]] entry maps a set of match criteria to an action and an optional per-route middleware stack. Routes are evaluated in declaration order; the first match wins.

[route.match]

Section titled “[route.match]”

All criteria are optional. A request must satisfy every criterion that is set.

[route.action] — proxy

Section titled “[route.action] — proxy”

Forward requests to a named upstream pool.

[route.action] — grpc

Section titled “[route.action] — grpc”

Forward gRPC traffic over HTTP/2 to a named upstream.

[route.action] — static

Section titled “[route.action] — static”

Serve static files from a directory on disk.

[route.action] — redirect

Section titled “[route.action] — redirect”

Issue an HTTP redirect.

[route.action] — respond

Section titled “[route.action] — respond”

Return a fixed response body without proxying.

[route.action] — mcp

Section titled “[route.action] — mcp”

Accepted by the parser, but not served from the config file: rws --check warns, and matching requests fall through to the static files. Mount MCP in code instead (see MCP).

[route.middleware]

Section titled “[route.middleware]”

Per-route middleware applied before the action. All sub-sections are optional.

A top-level [middleware] table (same keys and sub-tables as [route.middleware]) wraps every route and the static fallback.

[[tcp_proxy]]

Section titled “[[tcp_proxy]]”

Standalone L4 TCP proxy. Binds its own port and relays bytes bidirectionally between the client and a backend. Runs in a background thread and is independent of the HTTP server.

[[udp_proxy]]

Section titled “[[udp_proxy]]”

Standalone UDP datagram proxy. Each datagram is forwarded to a backend and the reply is relayed back to the originating client.

[[ws_proxy]]

Section titled “[[ws_proxy]]”

Standalone WebSocket proxy. Handles the HTTP upgrade handshake then relays raw bytes bidirectionally between client and backend.
