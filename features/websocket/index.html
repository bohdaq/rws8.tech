WebSocket

WebSocket routes

Section titled “WebSocket routes”

Since 18.5.0 a WebSocket endpoint is an ordinary route. The handler gets a WebSocketConnection once the 101 Switching Protocols response is out, and runs on a thread of its own for the connection’s life:

Router::websocket(pattern, |ws, params| ...) does the same in a Router, and inside any handler WebSocket::upgrade(request, |ws| ...) returns the 101 response and runs the closure with the connection. A request that isn’t a WebSocket upgrade gets 426 Upgrade Required.

ws.recv() returns Ok(Some(Message::Text | Message::Binary)) per message, Ok(None) after the closing handshake, and Err when the client disappeared or broke the protocol. Along the way it

  • joins fragmented messages (text is checked to be UTF-8 once whole),
  • answers pings with pongs and drops pongs,
  • answers the client’s close frame, and finishes one you started with ws.close(code, reason),
  • fails the connection with the right close code: 1002 for an unmasked frame, reserved bits or a bad fragment, 1007 for invalid UTF-8, 1009 for a message over max_message_size (16 MiB by default).

To send while recv waits, take a WebSocketSender — cloneable, usable from any thread:

sender.send_text, send_binary, ping and close all return Err once the connection is closed.

Notes:

  • HTTP/1.1 only, plain or TLS. Browsers open WebSockets over HTTP/1.1 unless the server offers RFC 8441 (WebSocket over HTTP/2), which rws doesn’t, so this is what they use.
  • Each connection holds a thread while it’s open: tokio’s blocking pool in async builds (up to 512 by default), a new thread in the http1 build.
  • No idle timeout: send pings yourself if connections can go quiet behind a proxy that drops them.
  • Server::process called directly, on a stream it can’t hand over, answers an upgrade with 500.

examples/realtime.rs has both routes above. ci/e2e/realtime.sh drives them from Node’s WebSocket client over plain HTTP and TLS, on the shared and per-core runtimes: echo with a 400 KB message, server-pushed messages from another thread, and clean closes started by either side.

Detecting upgrade requests

Section titled “Detecting upgrade requests”

Returns true when the request has all three required headers:

  • Upgrade: websocket
  • Connection: Upgrade (or any value containing “upgrade”)
  • Sec-WebSocket-Key: <base64>

Frame types

Section titled “Frame types”

Frame is an enum covering all RFC 6455 opcodes:

Variant Opcode Description
Frame::Text(String) 0x1 A complete UTF-8 text message
Frame::Binary(Vec<u8>) 0x2 A binary message
Frame::Ping(Vec<u8>) 0x9 Ping — respond with a matching Pong
Frame::Pong(Vec<u8>) 0xA Pong
Frame::Close(Option<u16>, String) 0x8 Close with optional status code and reason
Frame::Continuation { fin, data } 0x0 Continuation fragment for fragmented messages

Reading frames

Section titled “Reading frames”

Reads one complete frame. Client-to-server masking (required by RFC 6455) is handled automatically — the payload is unmasked before being returned. Extended payload lengths (16-bit and 64-bit) are supported.

A frame whose declared payload is larger than WebSocket::MAX_FRAME_PAYLOAD (16 MiB) is an error, returned before any of the payload is read, and the payload is read as it arrives rather than allocated at the size the client claims (since 18.1.0; before, a frame claiming an enormous length made the process abort). Writing frames

Section titled “Writing frames”

Writes one frame. Server-to-client frames are sent unmasked per the RFC. Payload length encoding (7-bit, 16-bit, 64-bit) is chosen automatically.
